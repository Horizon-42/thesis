# control 输出的约束方案（dev 文档，2026-09-05，第六版：屏障 v2、名义律 v2）

承接 `2026-09-04_constraint_methods_survey.zh.md`（方法综述）和 `2026-09-05_final_constraint_results.zh.md`（state 输出上的结果）。问题：**同一个五边约束（LPV 走廊 + 下滑道窗口）在 control 输出上，除了罚项，还能怎么加？**

## 结论

control 输出上值得做的是两条"进 rollout 回路"的路线，都作用在每一步的控制命令上，位置始终由动力学积分得到：

1. **屏障过滤器**：把走廊写成屏障，逐步算出坡度的允许区间，把网络的命令压进去。只在要越界时干预。
2. **名义跟踪律 + 有界残差**：门控生效时，命令 = 固定跟踪律（把飞机拉向中线和下滑道）+ 网络的有界修正。

两者接口相同、语义相反：过滤器只在命令要把飞机推出走廊（或已在走廊外、要求它回来）时改命令，名义律在门控段持续把飞机拉向中线和下滑道，网络只留有界修正。实现（2026-09-06，提交见 CHANGELOG）时确认：屏障条件 ḣ + αh ≥ 0 在 h < 0 时要求以 α|h| 的速率回到走廊，所以过滤器对已在走廊外但门控仍开（成员锥下限 500 m 内、路径对齐）的状态也会动作，与第一版"无事可做"的判断不同；它管不到的是门控关闭的行（离中线更远或方向不对）。参考路径 + 制导律、优化器求解、采样筛选降为低优先级；事后投影对 control 不适用。

## 出发点

- control 路径的 rollout（`control/dynamics/rollout.py`，点质量 + 一阶滞后，RK4 子步 0.5 s）整个在反向传播路径上，梯度经积分器传回控制量和分段时长。所以放进 rollout 的任何可微操作都自动进训练回路。
- 约束只能改**命令**，不能改位置。改位置（state 上的事后投影）会破坏动力学一致性，正好抵消 control 路径的意义。
- 已有的硬约束只有包线：控制头用 sigmoid 把推力比、坡度、载荷因子压进包线盒。走廊还没有任何硬约束。
- 罚项已经接到 rollout 端点状态上（`procedure_loss`，提交 9d9e66e）。KRDU 的结果：小剂量（1e-3）终点变好、路径中段变差、坡度略变平；大剂量（5e-3）全面变差，坡度调度坍缩成共享形状。罚项改变的是目标，不是可行集。
- 什么时候算"在五边上"（门控）是所有方案共同的难点。state 路径已有三种门：自门控（路径在成员锥内且方向对齐）、FAF 距离、真值。control 上复用同一套。

## 方案一：屏障过滤器

**是什么。** 安全强化学习里的"安全层"：策略照常输出动作，一个薄层在每一步把动作投影到不会越界的集合里。单个约束下这个投影有闭式解（Dalal 等人 2018），不需要 QP。

**怎么算。** 走廊写成屏障 h(x) = k·hw(d) − |xt| ≥ 0。点质量模型里横向位置由航向决定、航向变化率由坡度决定，h 相对坡度是二阶的，所以分两层一阶条件：

1. 位置层：左右两条屏障 h_R = k·hw(d) − xt、h_L = k·hw(d) + xt（xt 以航向右侧为正），条件 ḣ + αh ≥ 0。代入 ẋt = −V_h·sin ψ_err、ḋ = −V_h·cos ψ_err 和走廊收窄率 hw'(d)（阈值前 cw/d_GARP，过阈值为 0，`corridor_halfwidth_slope`），得到 sin ψ_err 的允许区间 [k·hw'·cos ψ_err − α·h_R/V_h, −k·hw'·cos ψ_err + α·h_L/V_h]：中线附近宽、贴边时只剩朝回中线的一侧；收窄项 k·hw'·cos 保证"贴着边平飞"也算越界（边在往里收）。区间为空（两边都越、或余量极窄）时收缩到中点。
2. 航向层：区间本身再当一对屏障（见"保持时长"），给出这一段内航向应当改变的量 Δψ ∈ [−βΔt(ψ_err − lo), βΔt(hi − ψ_err)]；坡度是一阶执行器（τ_bank = 2 s），一段之内飞机先以当前实际坡度 μ_0 飞 τ_eff = τ(1 − e^{−Δt/τ}) 的份额、再以命令 μ_c 飞其余，Δψ ≈ (g·L/V_h)·[tan μ_c·(Δt − τ_eff) + tan μ_0·τ_eff]（L = n·cos μ 是执行器状态里正在飞的垂直升力系数——界只依赖状态；载荷协调让命令的 L 与它一致，执行器稳定后两者相同），反解 tan μ_c 得坡度区间 [μ_lo, μ_hi]，再夹进包线 ±45°（两端都夹，区间不会反转）。位置层的余量也在"命令生效时"的位置上算（当前速度再飞 τ_eff）。这两处滞后补偿是 v2（2026-09-06）加的：v1 只用速率 ψ̇ = β·excess，在 7 s 保持 + 2 s 滞后下变成 +28° → −29° 的 bang-bang（见实验报告）。

区间由当前状态和跑道航向决定，都是解析式；梯度沿 rollout 传回前面的段。

**怎么压。** 训练回路里用 tanh 式软饱和：μ' = μ_c + w·(sat(μ_c; [μ_lo, μ_hi]) − μ_c)，w 是门控权重。软饱和是 C¹ 的，被夹住的步对命令仍有梯度；硬 clamp 在被夹住的步梯度为零（死区），只用于推理对照臂。`hard` 同时选硬饱和和硬门控（部署的过滤器没有"半开"的行），`soft` 是同一条规则的 C¹ 训练形式；所以"训练时穿过 hook"的价值要用同一个软 hook 的推理臂来对照（`F_barrier_infer_soft`），硬臂对照的是软硬这一对本身。

**屏障的收敛率 α。** 它决定过滤器多早介入：固定值要调；BarrierNet（Xiao 等人 2023）把 α 作为网络输出、随任务学出来，是这条路线的可微版本。第一版固定 α，"α 可学"作为一个开关，不另立臂。

**滞后。** v1 靠"α 保守"留裕度，不够：过滤器改的是命令，实际坡度 2 s 后才跟上，一段 7 s 的保持里前 2 s 还在飞旧坡度，下一段开始时航向已经越过区间另一边。v2 把执行器状态（`RolloutStateView.actuators` 的实际坡度）和保持时长一起写进屏障：命令只需补上这一段里"尚未被承诺"的那部分转弯，走廊余量在命令生效时刻的预测位置上评估。诊断记录被夹步比例（改动 > 0.5°）、区间塌成包线角点的步比例（保持时长 ≲ τ 时命令在段内几乎没有权威，反解的界爆掉、两端都落在包线上——1 s 保持时 24 % 的门控步，5 s 起为零；单独计数，免得把这个时长伪影读成“懒网络”）、每步平均坡度改动和载荷协调量；"实际坡度越出区间的步比例"仍是随手可加的下一项。

**载荷协调。** 只改坡度会丢掉网络配好的垂直升力分量 n·cos μ：v1 最差的航班在过滤器把坡度从 7° 抬到 28° 后，航迹角从 −1° 变到 −10°，速度 93 → 200 m/s，最后飞过阈值 16 km。v2 把载荷因子按 n' = n·cos μ/cos μ' 协调（夹进包线），保持网络要求的垂直分量；这不是下滑道跟踪，只是不破坏网络自己的垂直安排。

**增益。** 航向增益 β 的默认值从 0.3 降到 0.1（1/s）：带滞后补偿后 β·Δt = 1 意味着一段之内把全部航向偏差收回，30° 偏差要 45° 坡度；0.1 对应一段收回约 70 %、30° 偏差约 31° 坡度。α 仍是 0.1。

**保持时长。** 命令按段保持 Δt（部署时 64 段 / 中位 328 s ≈ 5 s，但时长头给长的航班可到十几秒），所以两个速率都是离散时间屏障：速率超过 1/Δt 就会在这一段之内穿过它要守的边（h_{k+1} ≥ (1 − αΔt)·h_k 要求 αΔt ≤ 1）。实现里每个增益取 min(增益, 1/Δt)，Δt 由 rollout 随状态一起交给 hook（`RolloutStateView.duration_s`）；航向区间本身也是一对屏障，允许的转弯率是 −β(ψ_err − lo) ≤ ψ̇ ≤ β(hi − ψ_err)——区间内朝边转的速率与到边的距离成正比，到边为零，越界后要求转回来，一条连续的规则，不是"区间内不管、越界才夹"（那样在边上不连续，而且区间内夹成 [0, 0] 是最初版本的错）。

**范围。** 第一版只做横向。下滑道窗口交给罚项或以后的载荷因子过滤器，避免两个过滤器在同一步抢命令。

**优点与短板。** 优点：最小干预，命令合规就原样通过，对已学好的调度几乎无影响；实现只在一处。短板：只管门控打开的行（成员锥下限 500 m 内且路径对齐）——走廊外但门控开的行会以 α·|h| 的速率被要求回来，门控关的行（离中线更远、或方向不对）不作为；不管垂直；网络可能学会"懒"——命令偏得很远、指望过滤器夹回来。

**检验。**
- 单元测试（`tests/test_command_hook.py`、`tests/test_control_constraints.py`，已有）：hook 恒等时端点和稠密 rollout 逐比特一致；读状态的 hook 改变路径且可微；点质量后端拒绝 hook；中线对齐的命令原样通过、朝边偏航的命令被抬到同一个回转需求、已足够回转的命令通过；走廊外但门控开的状态被要求回来，且保持一分钟时需求更温和；软版被夹步梯度非零、硬版为零；对抗命令（每段都朝右边压 20°）的硬版 rollout 在到阈值前每段都留在走廊内（留一段漂移的余量）；走廊收窄率等于半宽的差分导数。未做：随机命令的整体不变性扫描、"实际坡度越出区间"的计数。
- 读数：真值门控行上的走廊违反率下降，ADE/FDE 不退化（分层、两机场）；被夹步比例（> 20 % 且坡度技能低于基线减种子噪声，读作"懒"，否决）。
- 对照臂：训练不加、推理加同一个软 hook（`F_barrier_infer_soft`），量"训练穿过约束"值多少；推理硬夹（`F_barrier_infer`）量软硬之差。

## 方案二：名义跟踪律 + 有界残差

**是什么。** 残差策略学习（Silver 等人 2018、Johannink 等人 2019）和自动驾驶里"学习规划器 + 跟踪控制器 / 规则兜底"（SafetyNet，Vitelli 等人 2022）的分工，搬到 rollout 内部：一个已知稳定的控制律负责跟踪，网络负责有界的修正。也是真实自动驾驶仪的分工（LOC/GS 跟踪律 + 上层意图）。

**怎么算。** 门控生效的步上，网络命令被解释为对名义律的修正：

```
u_nominal(x_k)  横向：L1 制导（Park 等人 2004）把 xt 拉回中线，输出坡度
                纵向：下滑道跟踪，输出载荷因子
u_k'          = w_k · (u_nominal(x_k) + r(u_k)) + (1 − w_k) · u_k
r(u)          = tanh 有界残差；上限按观测航迹相对名义律的偏差标定（坡度约 ±5°）
```

门控关闭（w = 0）时与现在完全一样；门控打开时路径以名义律的收敛率趋向中线和下滑道，网络只能在残差上限内偏离。走廊保证不是逐点硬的，但由"名义律的收敛区间 + 残差上限"决定，可分析、可测。纵向增益同样受段保持时长限制（取 min(增益, 1/Δt)，否则一段之内航迹角就越过目标）；L1 律自身的时间尺度 L1/V ≈ 40 s 长于任何一段，不需要上限。

**推力：第三条律（v2，2026-09-06）。** 第一版推力透传，实验里名义律把飞机从下滑道下方拉回来时没有推力补偿，速度掉到 58 m/s（基线 88），落在阈值前 584 m。补偿不能只看这一段的航迹角变化：网络给的载荷因子在任何航迹角下都读作"保持当前航迹角"（trim 载荷 n ≈ cos γ 对任意 γ 成立），它想飞的 γ 从单段命令里不可观测，所以"抵消这一段变化"的协调只覆盖瞬态，飞机稳定在较浅的航迹角后减速继续。网络的意图只在它自己的 rollout 里。v2 让 hook 引擎对声明 `needs_reference` 的 hook 并行积分一条**无 hook 的参考状态**（多一次端点 rollout），`RolloutStateView.reference` 就是"网络自己的命令现在会把飞机放在哪"；推力做成对参考速度的比例保持 T' = T + k·m·(V_ref − V)（`control_nominal_speed_gain` = 0.1，时间常数 10 s，夹进包线）。它保留网络自己的减速意图，只补 hook 改路径的能量代价——与屏障保持 n·cos μ 是同一个原则。

**优点与短板。** 优点：从走廊外也能拉回；横向垂直一起覆盖；残差上限天然防"懒"；从锚点出发，没有起点问题。短板：名义律和数据打架的地方（真实航班在 10 km 处离中线 200 m 缓慢收敛）要靠残差上限留够；多两个要标定的量（L1 前视距离 / 增益、残差上限）；名义律本身要先对真实航迹验证。

**检验。**
- 单元测试（已有）：门控关闭时命令原样通过；门控开时坡度、载荷被压在名义值 ± 上限内，推力在参考速度处不变、比参考慢 10 m/s 时按 k·m·ΔV 抬起；从 80 m 高收敛到下滑道的 rollout，速度回到无 hook rollout 的 3 m/s 内（透传差 10 m/s 以上）；残差路径和状态路径都有非零梯度；残差压到 ~0 时，从 300 m 右偏、80 m 高出发，经一阶滞后 rollout 在到阈值前收敛到 |xt| < 60 m、高度误差 < 40 m，且都好于不跟踪的 rollout；制导律方向正确（右偏出正坡度、偏高出小于 cos γ 的载荷）。未做：名义律输出与逆动力学得到的观测坡度的相关性（可用 `score_control_arms.py` 的逆动力学坡度做，作为"名义律与数据打架"的底线）。
- 读数：同方案一；另加残差饱和步比例（> 30 % 读作"名义律与数据打架"，放宽上限或降增益）。
- 与方案一比较的关键维度：走廊外路径的回收率（门控生效时已在走廊外的行，之后进入走廊的比例）。

## 两个方案怎么选

| | 屏障过滤器 | 名义律 + 残差 |
|---|---|---|
| 对走廊内的路径 | 只在要越界时改 | 持续拉向中线 |
| 对走廊外的路径 | 门控开（500 m 成员锥内、对齐）则以 α·\|h\| 速率拉回，门控关不作为 | 门控开即持续拉向中线和下滑道 |
| 垂直通道 | 不跟踪下滑道，只协调载荷保持 n·cos μ（v2） | 覆盖 |
| "懒"的风险 | 有（要监控被夹步比例） | 残差上限限制 |
| 要标定的量 | α（或可学） | L1 增益、残差上限、速度保持增益 |
| 与数据打架 | 少（最小干预） | 可能（名义律的收敛率 vs 真实汇入速率） |

预期：直线进近两者都能压违反率；雷达引导航班只有方案二可能改善（它们的问题是路径在走廊外）；方案一更不容易伤到 ADE。两者共用门控、几何、诊断和读数，各自一个模块，先并行跑一轮再定。

## 其他方案

- **罚项**：已完成，实验中（`control_procedure_20260905`），结果另有报告。
- **决策量 + 封闭末段**（P2）：网络只预测汇入距离和时长，汇入后按程序几何闭式给出，控制量由逆动力学得到（`control/dynamics/inverse.py` 已有）。走廊从约束变成定义。适合直线进近；雷达引导航班汇入前那段仍要网络出。若两个 P1 方案都在直线进近上过关但雷达引导层没有改善，再做它。
- **参考路径 + 制导律**（低）：网络输出有界参考路径，制导律跟踪它出控制量。是一条新的输出路径，改动大；它与方案二共用制导律模块。只有当两个 P1 都失败、且原因是"控制头本身学不出五边意图"时再考虑。
- **优化器跟踪求解、采样 + 筛选**（低）：见综述 §2.5、§2.6。
- **事后投影**：不适用于 control。

## 接入方式

三条规则，够用即可：

1. **rollout 加一个 `command_hook`**（`rollout_control_endpoints(..., command_hook=None)`），签名 `hook(state_view, command_k, k) -> command_k'`，在**每个控制分段的起点**调用一次（不是每个积分子步：端点和稠密 rollout 都用手写伴随把整段控制序列当输入，子步中途改命令会破坏伴随；按分段调用则每段仍由伴随积分、段间靠普通 autograd，且"每段常值控制"的记录契约不变）。稠密 rollout 先用分段 rollout 定下有效序列，再用它稠密积分，轨迹一致。默认恒等（恒等时逐比特一致是第一条测试，`tests/test_command_hook.py`）。两个方案各是一个 hook 实现，放在 `control/constraints/`；rollout 不 import 它们，方向只有约束模块 → dynamics；hook 通过 `RolloutStateView`（图坐标位置、速度、执行器状态）读状态，不知道后端的私有布局，目前只有一阶滞后后端提供它。推理（`forecast` 的 control 批预测）用同一个 hook，训练和部署一致；`predict --command-hook … --hook-saturation …` 可以在推理时给一个没带 hook 训练的检查点套上 hook（安全层的经典用法）。记录里导出的控制量是有效序列，记录带 `commandHook` 字段。
2. **门控、几何、每航班常量复用 state 路径的**：`final_approach_geometry.py` 的公式和三种门；batch 上下文里的跑道航向和 tan GPA（`FINAL_APPROACH_KEYS`）。hook 不自己判断"在不在五边上"，它接收一个门控对象。
3. **诊断进 history，读数不加脚本**：每个 hook 报自己的计数（被夹步比例、残差饱和比例、门控权重 > 0.5 的步比例、每步平均坡度改动），走 `ControlLossTerms.diagnostics` 到 `EpochResult.command_hook`（按步数归一）；读数仍用 `compare_constraint_arms.py`（违反率、终点、分层配对）和 `score_control_arms.py`（坡度技能、共享分量），只加"走廊外回收率"：按预测自己的门（导出速度的航向 + 成员锥）取阈值前第一行门控开的行，若它在 k 走廊外则记为候选，最后一行门控开的行回到走廊内记为回收；表里是候选份额和回收率。

config 字段照 `PROCEDURE_LOSS_FIELDS` 的做法对命名配方开放，run 名显示为 `simple-v3+(…)`。
