# 读数：多机 7.7——失去间隔之后，倒回去让一架飞机重新说，救不救得回来（2026-10-02）

**问的是什么**：多机 7.6 的训练没有动（window r5 在验证集上没有站得住的好处，读数 [`2026-10-01_m4_window.zh.md`](2026-10-01_m4_window.zh.md) §5）。
设计里怀疑有三个原因，每一个要的改法都不同：
(a) 一句话只在最后给一个"成 / 败"，决定间隔的往往是冲突前几十秒里的几个词，分数却摊给整句的每个词，分不清是哪几个词的功过；
(b) 同一个窗口里所有由模型指挥的飞机一起换说法、一起失去间隔、一起扣分，分不清是哪一架的功过；
(c) 冲突在前几步就已注定，后面的词怎么换都避不开，那样换训练方法也没用。
7.7 量的是：**在一次失去间隔之前若干秒倒回去，只让一架飞机重新说，其余的飞机照它们原来说过的词飞，能不能避开这次失去间隔、并且还落地**。
这一步只量、不训练。读数用来定三件事：7.8（换训练方法，暂缓）重新开始时分叉放在哪里；先倒回哪一架；哪些事件是第 8 步（复飞）要对付的难事件。

怎么读是事先定下的（多机设计 §6.6 第 7 步"7.7 的细化"第 12 条，用户 2026-10-02 确认），本文 §5 照它原样用，不另加判据。

**几个词先说清楚**（全文用同一个意思）：
- **窗口**：一个机场里一段 20 分钟的到达流量。窗口里的飞机分两种：**被指挥的**（模型替它说话，执行器照词飞）和**照记录回放的**（按真实记录飞，不会因为别人的改变而变）。
- **判定**：判失去间隔的那一套规则（`inference/separation.py`，一个判定、两种读法）。**目视读法**（本文的判定与"落地"都用它）：按好天气下的目视进近许可来读，
  例如间距够大的平行跑道上两架都对准了各自的五边后不再判间隔；**IFR 读法**是仪表间隔规则照条文，更严（目视判出的，IFR 都会判出）；IFR 只报在旁边。
- **事件**：原来那一遍里，判定因失去间隔而结束了一架被指挥的飞机的每一次。开口前已失去间隔的不算。同一对飞机的一段连续失去间隔算一个事件。
  **事件的时刻 t_L** = 这一对第一次被判失去间隔的那一步（落地时的尾流间隔：那次落地的时刻）。
- **负责的**：判定结束的那一架（按规则它是该负责避开的一方，通常是后面的、或还在加入的那一架）。**对方**：这一对里的另一架，要求它也是被指挥的才有。
  **两架都负责**：这一段把两架都结束了；各做一遍，单列，不硬挑一架。
- **档**：重新说的那一架从哪一步开始重新说：t_L 之前 10、30、60、120 s（5、15、30、60 步，每步 2 s），以及**从头**（= 这一架飞机的第一个预测步，即模型接手的第一步）。
- **一次**（也叫一个分支）：把整个窗口从头再飞一遍，重新说的那一架在它的分叉步之前照原来的词、从分叉步起由模型自由说到底；**窗口里别的被指挥的飞机照它们原来说的词飞**
  （不因这一架的改变而改，问的就是"只靠这一架改，能不能避开"）；回放的飞机照记录。给定的词不采样、也不再过屏蔽。
- **格**：一个事件里一架重新说的飞机在一个档上的 8 次。一个"负责的"格就是一个事件（每个事件只有一个负责的）；"两架都负责"的事件有两架，所以有两个格。
- **救回来**（三条同时成立，设计第 10 条）：(i) 这一对从分叉步起不再失去间隔；(ii) 重新说的那架落地、落在机场此刻的落地方向上、没被结束（即奖励 1）；
  (iii) 没有新的失去间隔：这一遍里被结束的每一架，原来也被结束、而且是与同一架飞机（没有把冲突推给别的飞机）。表里三条也各自报。
- **至少一次**：8 次里至少一次救回来的格占的份额——"挑得出来"的上限。**平均每次**：每次救回来的概率（每格 8 次，所以等于全部次数里救回来的份额）。

## 1 怎么量的，量了多少

### 1.1 步骤

1. **原来那一遍**：每个窗口让模型把所有被指挥的飞机一起说一遍（R34 的"窗口里一起"读法，每窗口 1 次，随机数流同 R34），执行器一起飞，判定一路记下每架说的词和每一次失去间隔。
   扩充窗口是同一批窗口加扩充（种子 7919）：A 插一架、B 挪一架的起点、C 压紧流量。
2. **事件**：从原来那一遍里找出事件（上面的定义）。
3. **分叉**：对每个事件，由负责的 / 对方（对方是被指挥的才做）/ 两架都负责的每一架，每个档做 8 次。不做、计数的见 §1.3。
4. **对照**：每个事件另飞一次"所有词照原样"，必须与原来那一遍相同：说的词、结局、判定记下的每一次失去间隔等离散的项逐个相等，浮点的项差在 1e-6 以内，否则运行停下报错。
   它核对的是"倒回去"这件事本身没有改变任何东西。
5. **读**：每一次按"救回来"的三条判，汇成格，再按角色 × 档、按分组汇总。

### 2.4 读

测量：
1. **越早倒回去，救回来越多，每一档都比下一档低**。"负责的"至少一次：真实 3.1 → 13.0 → 25.4 → 41.7 → 69.6 %，扩充 1.4 → 8.2 → 17.7 → 37.9 → 54.2 %（10 s → 30 s → 60 s → 120 s → 从头）；
   平均每次：真实 1.1 → 4.9 → 9.1 → 17.4 → 32.7 %，扩充 0.5 → 2.7 → 6.3 → 13.2 → 22.6 %。
2. **短档接近零，与事先预计的一致**：10 s 档"负责的"真实 7 / 226、扩充 5 / 352 个格有过一次；30 s 档真实 13.0 %、扩充 8.2 %，仍低。"对方"在 10 s 一次都没有（0 / 115、0 / 199）。
3. **"从头"这一档，8 次里 3 次及以上救回来的格**：真实 105 / 227 = 46.3 %、扩充 107 / 358 = 29.9 %；一次都没有的真实 69（30.4 %）、扩充 164（45.8 %）。
4. **三条里最紧的不是同一条**：负责的在"从头"，落地（真实 38.9 %，扩充 29.8 %）和这一对不再失去间隔（50.1 %，39.0 %）比"没有新的失去间隔"（78.4 %，77.0 %）低得多；
   "对方"的落地一直很高（65–95 %，因为它在原来那一遍里没被结束，不改也多半落地），卡的是这一对不再失去间隔（"从头"才到 38.3 % / 35.3 %）；
   "两架都负责"的落地在短档很低（10 s 只有 3.5 % / 2.8 %，原来那一遍它们都被结束了）。
5. **"没有新的失去间隔"随倒回得越早越低**：负责的从 98.6 %（10 s）降到 78.4 %（从头，真实）、98.5 % 降到 77.0 %（扩充）。
   也就是从头重新说的次数里有五分之一多（真实 21.6 %，n = 1,816 次；扩充 23.0 %，n = 2,864 次）把冲突换成了别的失去间隔（别的飞机，或同一架飞机被判与另一架飞机）。

我的读法：
- 7.7 开头问"冲突是不是前几步就注定了"（原因 (c)）。短档救不回来是预计中的；但倒回 120 s、尤其倒回"从头"之后，有相当一部分事件至少能救回一次，所以**不是所有冲突都注定了**，至少"负责的"这一架从接手起还有路。
- "至少一次"是 8 次里挑最好的，是上限；平均每次才是随手抽一次的机会：真实"从头"约三分之一，扩充约五分之一。两个数之间的差就是"挑得出来"要补的部分（§5）。

## 5 按事先定的读法下结论（设计"7.7 的细化"第 12 条，用户 2026-10-02 确认）

**事先定的读法**，原文意思：
- 短档（10、30 s）预计接近零，不作判断依据；
- 主要看"从头"和 120 s：
  - "从头"8 次里至少一次救回来的事件占**三分之一以上** → 模型接手时就说得出好的选项，只是挑不出来 → 7.8 重新开始时，分叉放在开头和定时的几个点上（S2），不放在出事后倒回几十秒（S1）
    （S1、S2 是设计里 7.8 草稿的两种放法：S1 = 正常往前飞，出事了才倒回去几十秒重新说；S2 = 分叉放在开头和定时的几个点上）；
  - "从头"**也不到一成** → 25 km 处交过来已经来不及：交给复飞（第 8 步），或让窗口从更远处开始；
  - **介于两者之间**，与用户一起看分组（真实、扩充分开）再定；
- "从头"8 次都没救回来的事件列出来（§6）；
- "负责的"与"对方"哪个救回来的多，决定 7.8 重新开始时先倒回谁（§7）。

**测量**（负责的；二项分布 95 % 区间是我按事件相互独立算的，没计窗口内的相关，所以偏窄）：

所以按事先定的读法，属于第一种情形：**模型接手时就说得出好的选项，只是挑不出来；7.8 重新开始时，分叉放在开头和定时的几个点上（S2），不放在出事后倒回几十秒（S1）**。

我的读法（这些不改规则给的结论，是要带着的限制）：
1. **"挑得出来"是 7.8 要回答的，7.7 没回答。**"至少一次"是事后看 8 次里有没有一个好的；真正要的是不看结果就挑出那个好的。平均每次只有 32.7 % / 22.6 %，
   随手抽一次，真实窗口里三次约一次、扩充五次约一次成。
2. **不是只靠运气抽到**：8 次里随手抽，哪怕一个事件每次只有 5 % 的机会，8 次里至少一次也有 33.7 %（1 − 0.95⁸）；但"从头"8 次里救回来 3 次及以上的格，真实占 46.3 %（105 / 227）、扩充 29.9 %（107 / 358），
   这些事件每次的机会是不低的。
3. **这些事件比一般的飞机难得多**：原来那一遍里所有被指挥的飞机结局为落地的占 83.7 % / 77.8 %，而事件里负责的那架"从头"重新说，落地（奖励 1，口径略严一点：要落在机场此刻的落地方向上）的只有 38.9 % / 29.8 %。

4. **一个仍要看分组的地方**：整体过了三分之一线，但**扩充窗口里直线的飞机"从头"28.8 %（47 / 163）、开口不到 120 s 就失去间隔的事件 27.8 %（35 / 126）、插进来的那架当负责的 29.8 %（17 / 57）、KSJC 31.5 %（28 / 89）**，

5. **120 s 档也过了三分之一**（41.7 % / 37.9 %），但只含离开口不少于 120 s 的事件（§3.3）；规则对 120 s 没有给线。不要因此把"出事后倒回 120 s"当成可行的 S1：

   **直线 + 尾随**是最大的一类：真实 25 个（占难事件 36.2 %；这一类 41 个格里 61.0 %）、扩充 65 个（39.6 %；85 个格里 76.5 %）。
3. **机场**：KSJC 最多（真实 23 个，占 33.3 %；扩充 61 个，占 37.2 %），同时 KSJC 的直线飞机占比最高（§3.2）。真实的 KMSY 难事件占 58.8 %，但只有 17 个格。
4. **扩充的种类**：A 插一架占 62.2 %（102 个）；其中插进来的那架当负责的 57 个格里 40 个是难事件（占全部难事件的 24.4 %）。B 挪起点只占 10.4 %（17 个）。
5. **离开口近**（§3.3）：难事件里一半以上离这架开口不到 120 s（真实 35 / 69 = 50.7 %，扩充 91 / 164 = 55.5 %）；
   反过来，不到 120 s 的事件里 67.3 %（35 / 52）/ 72.2 %（91 / 126）是难事件，不少于 120 s 的事件里这个比例是 19.4 %（34 / 175）/ 31.5 %（73 / 232）。
   难事件的开口前时间（可知的）中位 117 s（真实，n = 68）/ 109 s（扩充，n = 158），不是难事件的 295 s / 283 s。
6. 对方是被指挥的还是回放的：真实里对方被指挥的 144 个事件中 40 个难（27.8 %），对方回放的 83 个中 29 个难（34.9 %）；扩充 108 / 231（46.8 %）与 56 / 127（44.1 %）。差别不明显。

### 6.2 8 次里它们怎么失败的

| 难事件的 8 次里……（格数） | 真实（69 个） | 扩充（164 个） |
|---|---|---|
| 没有一次这一对不再失去间隔、也没有一次落地 | 38 | 96 |
| 有过这一对不再失去间隔，但从没落地 | 15 | 31 |
| 有过落地，但这一对从没避开 | 4 | 18 |
| 两样都有过，但不在同一次里 | 5 | 4 |
| 同一次里这一对避开了也落地了，但把冲突推给了别的飞机（第 (iii) 条不成立） | 7 | 15 |

难事件的 552 次（真实）/ 1,312 次（扩充）里，这一对不再失去间隔的占 16.3 % / 13.4 %，落地的占 7.4 % / 8.1 %，有新的失去间隔的占 25.9 % / 23.7 %
（不是难事件的格，1,264 次 / 1,552 次：64.9 % / 60.6 %、52.7 % / 48.2 %、19.8 % / 22.5 %）。重新说的那架最后的结局：被判失去间隔 88.9 % / 90.7 %，落地 8.3 % / 8.2 %，超时 2.0 % / 0.7 %，其余不到 1 %。
也就是它们大多数是"重新说也还是撞上"，不是"避开了但落不了地"；少数（真实 7、扩充 15 个）是避开了也落地了但冲突转到别的飞机身上。

### 6.3 对方能不能救

负责的救不回来的事件，**对方从头至少救回一次**的：真实 28 / 40（70 %）、扩充 50 / 108（46 %）（只算对方也被指挥的事件）。
负责的和对方都"从头"一次都救不回来的事件：真实 12 个（占 144 个有对方的事件的 8.3 %）、扩充 58 个（25.1 %）。
"两架都负责"的格里，"从头"8 次都没救回来的：真实 36 / 121 = 29.8 %，扩充 107 / 211 = 50.7 %。第 8 步的难事件按设计 8.4 只含负责的那架；这几个数只作背景。

我的读法：
- 难事件的主体是"直线的飞机、同一条进近上前后、离模型开口不到 2 分钟就失去间隔"。我的猜测是：这类飞机接手时已排在别的飞机后面、离冲突很近，可用的手段少
  （§4 里救回来的次更常改的是航向和进近许可，这类飞机能改的余地小）；7.7 没有直接检验这一点。
- 因为"从头"重新说也救不回来的事件里，一半以上本来就是模型刚接手就快失去间隔的，所以它们更像是**第 8 步复飞能不能救**的问题，而不是 7.8 的分叉放在哪里的问题；
  这与规则第二种情形的说法（"25 km 处交过来已经来不及"）对得上，只是它只适用于这一部分事件，不是整体。

## 7 负责的与对方，哪个救回来的多

**看主表（§2.1，各自的全部格）**："负责的"在每一档都比"对方"救回来的多：

| 档 | 真实：负责的 / 对方（至少一次） | 扩充：负责的 / 对方 |

| 档 | 数据 | 事件数 | 只有负责的救回来 | 只有对方救回来 | 两个都救回来 | 都没救回来 | 负责的至少一次 | 对方至少一次 | 两者之一 |

测量：
1. **倒回 60 s 或 120 s 时，负责的明显好于对方**：同一批事件上 120 s 档 49.3 % 对 15.9 %（真实，n = 69）、49.5 % 对 13.6 %（扩充，n = 103）；60 s 档 23.7 % 对 8.6 %、20.8 % 对 5.0 %。
2. **"从头"时两者接近**：72.2 % 对 60.4 %（真实，n = 144）、53.2 % 对 48.9 %（扩充，n = 231）；对方能救、负责的救不了的事件不少（28 / 144、50 / 231）。

## 8 要打折的地方

1. **每个窗口只飞了一遍原来的**：有哪些事件取决于这一次随机抽样，换一遍会是另一批事件（也不是每个事件都"注定"）。7.7 的事件今天的代码重放不出来（§6）。这些数是"这一遍随机抽样里出事的那些事件"，不是"模型一定会出事的情形"。
2. **每格只有 8 次**：①"至少一次"是 8 次里挑最好的，是上限，不是随手抽一次的机会；②平均每次的估计，一格里的 8 次只有 0.125 的分辨率，要靠大量格平均才可靠。
3. **选择集的运行日（9 天）、一个模型（traffic r5）、一个读法（目视）**：IFR 读法更严，原来那一遍里失去间隔就多 2 个百分点（14.5 对 12.2 %，扩充 20.1 对 18.1 %），救回来的份额在 IFR 下应当不会更高（我的读法，没有量）。验证集、测试集没有碰。
4. **别的飞机不会反应**：重新说的那架之外，被指挥的飞机照它们原来说的词飞，回放的飞机照记录。这是设计要问的"只靠这一架改"，但真实中别的飞机、管制员都会跟着变；这里量到的是"一架的单方面改变"的效果，不是"整个系统重新协调"。
5. **窗口里的事件不独立**：207（真实）/ 346（扩充）个窗口里的 294 / 477 个事件，同一窗口的几个事件共用原来那一遍；"两架都负责"的两个格属于同一个事件；真实、扩充是同一批窗口。区间和份额都没有按窗口聚类，**偏窄**。
6. **分组里的小格**（† 标出）：不到 20 的格都只当线索；多个分组同时看时，组合更小（机场 × 类型的格最多 56 个、最少 4 个，多数 10–50 个）。
7. **120 s 档与"从头"档不是同一批事件**（§1.3、§3.3）；不同档的"改了几步词"也不能比（§4）。
8. **说话飞机的类型是按它记录下来的航迹分的**，不是按模型这一遍飞出来的航迹，两者不一定同一类。
9. **没有训练、没有复飞**：这里量到的是同一个模型（traffic r5）的重新说，没有说明训练能不能学会挑出好的那一次，也没有任何复飞的词（7.7 的运行早于第 8 步）。
10. **模型的"随机"只有温度 1.0 这一档**，没有试别的温度；更低的温度会让 8 次更像，更高的会更散，对"至少一次"的影响没有量。

## 9 数据里要留意的几处

- **schema 是 `ts-traffic-window-rewind-v1`**（两个 `window_rewind.json` 里都是）。v2 是第 8 步 8.1–8.2 的提交（`00e86888`）改的，v3 是 `ef2eeb54`；这次运行用的 `3615ac2c` 是 v1。
- **`window_rewind.json` 里的 `drawn` 块是扩充之前的抽样**，两个文件里一样（1,000 个窗口、2,867 架），扩充运行的窗口数和被指挥的飞机数要看 `augmenting` 和 `original`（996 个窗口、3,184 架；汇总里 3,143 架）。
- **`original.scene.aircraft` 不含开口前已失去间隔的飞机**（真实 2,844 = 2,867 − 23；扩充 3,143 = 3,184 − 41），而事件里"两架都负责"的格位含这样的飞机（真实 13、扩充 27 个，它们没有格，§1.3）。
  所以"负责的 + 两架都负责的格位"（真实 227 + 134 = 361）比原来那一遍里被判失去间隔的飞机数（348）多 13，正好是这 13 个。
- **"两架都负责"的格位数是飞机数，不是事件数**：真实 67 个事件对应 134 个格位，扩充 119 个对应 238 个。
- `run.log` 在两个目录里是同一个文件（含两次运行的全部输出）。表里的数我都从 `events.jsonl` 重算过，与 `window_rewind.json` 的 `readout.pooled` 和 `readout.groups` 逐项相等（真实 1,890 项、扩充 2,156 项，无差别）。
- 设计里预估事件"约 350 个"（真实）；实际 294 个。预估"扩充再约一倍"；实际 477 个，是真实的 1.6 倍。
