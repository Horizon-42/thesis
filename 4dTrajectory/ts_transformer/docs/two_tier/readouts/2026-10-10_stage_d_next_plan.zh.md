## 2. 信用和训练

### R1 B 点换成"多数能避开的点"（已实现，172bc07d，未合并）

**用户的话（2026-10-10 晚）**："直接把 B 换成多数能避开的点，至少 5 条；但是现在先不实现。"

- **现在（D182 第 6 步）**：决策点之后继续往回，找第一个"至少 1 条续说避开事件，而且 v 从这点到事件 + 60 s 没说复飞"的点（B）。
- **改成**：决策点之后继续往回，找第一个"K = 8 条续说里至少 5 条避开事件"的点（下面叫 M 点）；它的 8 条续说飞到窗口结束，
  和第一句一起成一组。B 点删掉。"避开"的定义不变（D182 第 3 步：到事件 + 60 s，v 不承担任何失去间隔，事件没发生）。
- **为什么**：决策点是最晚、最难避开的点，常常只有 1 条续说靠一次侥幸的晚动作避开；那里学到的是只适合那一次几何关系的最后关头动作，
  各组之间没有共同的东西（梯度一致性读数）。多数续说都能避开的点上，平常的说法大多可行，该学的是更早、更温和的调整（减速、拉开间隔），
  更可能在不同冲突之间共通。
- **实现前要定的细节**（Claude 列的，等用户定）：
  1. 8 个点 / 256 s 内没有 M 点时：不成组（同今天"找不到就不成组"），还是放宽往回的上限。
  2. 决策点自己是 M 点（8 条里已有 5 条避开）时：只成一组。
  3. 16 s 细点（D182 第 5 步）留不留。
  4. M 点要不要也要求"没说复飞"（今天 B 的条件）。
  5. 读数加上 M 点的深度分布、找到 M 点的搜索占比。
  6. 写进 `multi_control.md`：新 D 号（下一个空号 D192），改写 D182 第 6 步和 §2.3 的那段；设置名（例如 `backward` 的一个新取值，
     默认是今天的行为）。
  7. 核对：grid 不动，逐位相同；backward 的组会变，按 D188 的方式在固定输入上核对搜索规则。

### R2 数据项占比太大（提议，等用户定）

- **现象**：先验每次更新里数据项占约 45%，而且方向非常一致（两半一致性 0.95）；奖励项占约 55%，但方向是噪声。
  结果是一整轮下来，先验稳定地被拉向模仿记录（整个更新的两半一致性 0.83），奖励只在上面加随机抖动。AdamW 按每个参数的梯度大小归一，
  数据项的梯度也占掉了每一步能走的幅度。
- **可选的改法**（都是现有设置，或默认为今天行为的新设置）：
  1. 数据项权重 1 → 更小（例如 0.25）。现在是 `post/loss.py` 的模块常量 `DATA_WEIGHT = 1.0`（拉回 `KL_WEIGHT = 0.04` 同），
     要先改成 campaign 设置（默认 1.0 = 今天的行为）；stage C 提过同样的消融（`readouts/2026-10-08_stage_c_next_steps_proposal.zh.md` T3），没做。
  2. 每次更新的数据句子数 `data_sentences` 64 → 更少（注意：这是 profile 记录的设置，改了要重新量内存）。
  3. 数据项不是每次更新都算，每 N 次算一次。
- **风险**：数据项的用途是让先验不忘掉基础说话（post-training D36）；拉回项现在占比 ≈ 0，靠不住。数据项调小以后，要看
  模型的说话有没有偏离（teacher-forced 数据项损失、KL、语法/程序掩码拒绝的比例）。
- **怎么验证**：和学习率对照一样，同起点、同种子、同窗口跑 2 轮，只改数据项。最好在 R1 实现之后做：现在奖励项是噪声，
  数据项调小也只是让噪声占得更多。

### R3 只训交通模块的对照（提议）

- 先验学习率 0，交通模块 1e-4 不变；同起点、同种子、同窗口跑 2 轮，约 2.5–3 小时。
- 目的：检验今天的小增益是不是主要来自交通模块（那里的奖励梯度有弱的共同方向）。如果降落率保持或上升、不稳定进近不再涨，
  说明先验的奖励更新现在只在加噪声。
- 先查 runner 收不收学习率 0（AdamW 的 weight decay 乘学习率，0 时也不动）；不收就是冻结先验的小改动。

### R4 梯度累积（提议，配合用）

- 做法：连续算 N 批（每批仍是 `update_groups = 4` 组）的梯度，加起来取平均再走一步；内存不变。新设置，默认 1 = 今天的行为。
- 只能把已有的共同方向显出来；先验的奖励梯度现在没有共同方向，单用不解决问题。用在交通模块（有弱信号）或 R1 之后。

### R5 信用摊得太宽的读数（待做，只读盘上的数据）

- 一组里 1 条续说避开时，奖励抬高 v 从分支点到事件的每一个词（中位 33 行，约 130 s），真正起作用的可能只有一两个词。
- 读法：第 5 轮盘上的组（92 批，`multi_train_20261010/round_5/groups_*.pt`；MC6 续跑并跑完第 5 轮后这些组会被删），
  对每组比避开的续说和失败的续说：分支点后各行的词有多少不同，差别是不是集中在头几行。
- 结论成立的话，信用设计可以加一条：只给分支点之后的头几行记优势。
- **读数（2026-10-10 夜，`outputs/POOLED/multi/handover_20261010/r5/`）**：第 5 轮盘上 92 批、663 个分支组（盘上只存回报有差别的组），
  5,967 句。优势从分支点算到事件：中位 33 行（四分位 17–56），其中说了词的行中位 12 行。回报不同的两句和回报相同的两句，
  在分支点那一行就分开的比例差不多（65 % / 61 %）；两句不同的行里落在分支点后头 8 行的份额，回报不同的反而更小（34 % / 42 %），
  回报不同的两句不同的行更多（中位 19 / 15 行）。**差别不集中在头几行**：按词看分不出哪几行起作用，"只给头几行记优势"没有依据。
  （词不同不等于起作用；这只是词面的读数。）

### R7 起点先做拒绝采样微调，再训交通模块对照（提议，等用户定）

- **想法（用户 2026-10-10 晚提出）**：用 MC6 的起点模型把窗口说多次，只留好的句子，用它们做 teacher-forced 微调（拒绝采样微调），

## 3. 提速

一轮现在约 75–80 分钟（3 GPU + 3 CPU worker，说话约 60 分钟，训练那一遍约 16 分钟）。下面的收益数都是 Claude 的估计，不是实测。

### S1 GPU worker 的执行器放 CPU（代码完成，2961b99a）

- GPU 上执行器比 CPU 慢：第 86 批整批 21.1 s 对 12.8 s，第一遍 10.3 s 对 3.9 s（小运算，GPU 启动开销大）。窗口循环也是 GPU 慢（20.8 对 16.2 s）。
- 估计每个 GPU 批快约 20%。然后按新速度重调 `cpu_batches` / `cpu_period`。
- 核对：执行器换设备后最后几位会变，按 D181 (57) 的界核对（词和结果相同，边界附近的抽样计数，状态在 `STATE_BOUND_M` 内）。
- 做法：进程选项 `--executor-device cpu`（`multi_train`、`multi_speed`），不是活动设置；默认 `speak` 就是原来的行为，逐位相同。
  `Context.start_loop` 在 CPU 上起执行器，`SpeakingLoop` / `WindowLoop` 明确拿到这个设备，拷到主机（D182）和合并（D188）时都留在 CPU。
  每批的记录写上执行器的设备。合成窗口的 GPU 测试：词相同，状态差在 1e-6 m 内。
- 还没做：真实窗口上的界核对、第 86 批 GPU 计时。都要 GPU，等只训交通模块的对照跑完。

### S2 窗口循环整批计算（完成，88a3990e）

- 先测再改：第 86 批第二遍的 CPU 剖析（`outputs/POOLED/multi/speed_mc7_r0_b86_cpu_profile_second_20261010`）。窗口循环里最大的
  一块是已经不飞的行的交通 token：每步约 46 行，每行单独算一次，每次都重算录制飞机的运动、进近时钟和一张新的跑道对表。
- 改法：一个窗口里不飞的行看的是同一批录制飞机，一次算完（`edges.each_tokens`，`WindowLoop._alone`）。逐位相同：
  `window_behaviour` 对 S1 提交在 MC6 的 stage D 窗口（第 0、23、86 批）和 stage C 的 seg60 窗口上 "the same behaviour"，
  `prior_behaviour` 相同。
- 实测（两份代码同时跑，同样的负载）：第 86 批 CPU 窗口循环 20.1 → 17.6 s（−12%），整批 84.3 → 81.5 s（−3%）。比估计的小：
  剖析器把 Python 开销放大了约 1.6 倍。
- 试过但没用：说话器的跑道词掩码按跑道词一次算（`_runway_allowed`），结果逐位相同，但 64 行以上反而慢（256 行慢 4 倍：数组变大，
  放不进缓存）。审查发现后撤掉。

### S6 联合循环里已经不飞的行（提议，改设计）

- 第 86 批的反向搜索平均每步 135 行（465 步，62,776 行），其中约 46 行已经不飞（降落了，或失去间隔后结束），但窗口里还有别的飞机在飞，
  所以这些行留在批里：说话器照样说（词丢掉），执行器照样飞（停住的飞机），token 照样算。它们的词和状态没有任何地方再读。
- 去掉它们（例如在联合循环重建时只留还在飞的行）能省说话器、执行器和 token 约三分之一的活。这改的是 D188 的联合循环
  和"不飞的行照常说"的写法，要设计者写、用户定。逐位相同可以做到：被去掉的行的输出本来就没人读。

### S3 各跨度按成本分配窗口个数（提议，O21）

- 1200 s 窗口占一轮约 60% 的批，每个有信息组的成本是 300 s 窗口的约 2.6 倍。给它们按成本分配个数，每小时有信息的组估计多 1.5–2 倍。
- 代价：训练分布偏向短窗口。改的是 D146 的"各跨度等分"，用户定。

### S4 CPU worker 的主机内存兜底（提议）

- 一个 CPU 批能让 worker 超过 4.7 GB；4 个 CPU worker 时 swap 被挤满。GPU 批有"超份额重说"兜底（e2b69736），CPU 批没有。
