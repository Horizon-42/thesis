AeroViz-4D · ts_transformer · KSJC

KSJC Label Decoder

Every entry in the Observe panel's Prediction and Experiments pickers is named by one grammar, derived mechanically from the run's stored config. This page expands each part of that grammar, then walks all 27 KSJC categories family by family. Single source of the grammar: 4dTrajectory/ts_transformer/run_naming.py.

01

Anatomy of a label

Validation split (model selection) — Predicted:
control· iTransformer· first-order-lag @scaled-transport-chart-velocity· simple-v2+(vel=0.05)· d-model=512, d-ff=1024, layers=4, N=64, batch=512, lr=3e-05, +4 more, wiggle_loss_design/velocity_32x
1 output 2 backbone 3 dynamics 4 loss design 5 meta

The prefix says which data the numbers describe: Training split (in-sample) — flights the checkpoint saw, error measures fit, not skill; Validation split (model selection) — held-back flights, the number to compare models on. The split is by flight, never by window, and is persisted inside the checkpoint (config.py, dataset.py). Predicted: marks a primary result under the Prediction source; Experiment: marks an arm of a sweep published with checkpoint metadata for the grouped picker — a publisher flag (--result-source), not a property of the model. The five slot colours above are used for the same slots throughout this page.

02

Output & backbone

TokenMeaning
state The purely kinematic baseline: chart channels in, future chart channels out, no dynamics anywhere — deliberately, so the learned component is measured on its own. No flyability guarantee.
control The model emits a bounded control schedule — thrust fraction ∈ [−0.2, 1.0], bank ∈ ±45°, load factor ∈ [0.2, 2.0] (control/envelope.py) — and a differentiable RK4 rollout of the shared point-mass equations turns it into the trajectory. Every prediction is dynamically admissible by construction.
iTransformer Attention across channels (variate tokens). Vendored byte-identical in vendor/itransformer/.
PatchTST Channel-independent patched attention along time (vendor/patchtst/). Channel independence cannot represent a turn's east/north coupling — one reason it trails at long horizons.

Defined in config.py: PREDICTION_STATE / PREDICTION_CONTROL, MODELS; instantiation in models.py. Rationale: the "prediction_output decides whether dynamics is connected at all" entry in the package CLAUDE.md.

03

Dynamics — the flight model behind the rollout

TokenMeaning
kinematic State output only: no dynamics attached (see slot 1).
point-mass Each commanded control is applied instantly — controls have no derivative.
first-order-lag The three controls become actuator states driven toward the commands through first-order ODEs — controls have a derivative. τ = 1.5 / 2.0 / 0.8 s (thrust / bank / load); a non-default τ appears inline, e.g. first-order-lag(τ-bank=4s). It wraps the same force equations as point-mass: one flight model plus three actuators, not a second model.
@scaled-transport-chart-velocity The rollout backend — the state representation the long rollout integrates — shown only when it differs from the default reanchored-rk4 (local-ENU RK4, re-anchored into geodetic state each sub-step). The scaled chart variant integrates threshold-chart position + moving-local-ENU physical velocity with the full WGS84 transport rate, normalized. Every KSJC control run uses it.

Defined in config.py (CONTROL_DYNAMICS_MODELS / CONTROL_DYNAMICS_BACKENDS); the registry keyed by the (model, backend) pair is control/dynamics/backends.py. The two axes are orthogonal — physics vs state representation.

04

Loss design — what training scored

RecipeWhat it scores
simple-v1 True-time position at the 64 segment endpoints + final time + endpoint term; point-mass dynamics. Its measured failure: position-only supervision let 71 % of predicted bank energy collapse into one shared wiggle profile.
simple-v1-lag Same objective, first-order-lag dynamics. The τ_bank CV sweep ran on this.
simple-v2 v1-lag + velocity term (vel = 0.003 ≈ 2× the position term at convergence). Fixed the shared-wiggle profile: 71 % → 17.3 % shared.
simple-v3 v2 + direct control imitation (imit = 64 ≈ 47× position) against the inverse-dynamics teacher (control/dynamics/inverse.py). Current recommended recipe; the weight is per-airport — 64 overshoots on KSJC.
state-v1 The state output's formal objective — normalized position MSE + duration + endpoint term — at its frozen coefficients.

Custom runs are named against their nearest recipe — the one whose frozen loss fields need the fewest edits to reproduce the run, edits in parentheses: simple-v2+(vel=0.05) is exactly simple-v2's loss with the velocity weight moved 0.003 → 0.05. A run matching a recipe exactly is shown as that recipe bare, even though its config says custom (CV/dev runs are always stamped custom — a named recipe cannot be cross-validated as itself). More than four edits collapse to a stable content hash: custom-3f2a91bc.

Edit abbreviations: vel = control_velocity_loss_weight, imit = control_imitation_loss_weight, obj = control_state_objective, grid = control_state_loss_grid, clock = control_state_supervision_clock (full map: run_naming._ABBREV). Recipes: config.py CONTROL_RECIPE_* + control_recipe_overrides() — frozen fields raise on mismatch.

What "direct control imitation" is — and what imit sets

The gap it closes. Every earlier term scored what the controls produce: position is derivative order 0, the v2 velocity term order 1 — but bank lives at order 2, so no term ever named the controls themselves. Measured on the pre-v3 models: the predicted bank carried less information about the flown bank than a randomly chosen other flight's bank did (per-flight skill +0.124 vs a random-flight floor of +0.170 on KRDU) — the model learned that banking happens, never when.

The mechanism. For every training flight, the observed trajectory is pushed through the exact inverse of the configured forward dynamics (control/dynamics/inverse.py) to recover the control schedule — thrust fraction, bank, load factor per segment — that would reproduce the flown track under that flight model. The network's emitted schedule is then penalized for deviating from this recovered schedule, channel by channel: it supervises the controls themselves, not only the trajectory they roll out to. The inverse is registered under the same config key as the forward model (target and rollout can never be different equations; round-trip-tested in tests/test_control_inverse_dynamics.py), and the target is built on the training-only path (dataset.reference_control_supervision) — inference has no future track to invert. Each channel is divided by half its envelope width (control/envelope.py), which gives the term a per-airport split: thrust/bank/load carry 57/41/2 % on KRDU but 82/18/1 % on KSJC — the root of the "recalibrate the weight per airport" rule.

What the imit number is. The raw value of control_imitation_loss_weight, the multiplier on this term in the total loss. The "≈ 47× position" gloss is a calibration at the converged KRDU baseline where w = 1.36 equals 1× the position term — so imit=64 ≈ 47×, imit=16 ≈ 12×, imit=256 ≈ 188×. The dose curve is not a ramp: below ~12× a noisy plateau, ~47× the sweet spot frozen into simple-v3, past it saturation and overshoot — at ≈188× the predicted bank comes out smoother than the flown tracks themselves. At the frozen 64, on 1404 KRDU validation flights: bank skill 0.124 → 0.735, flight-independent bank share 49 % → 3.3 % (flown: 1.8 %), straight-in bank RMS 3.92° → 0.36°, ADE better on 57 % of flights, FDE unchanged.

Not the same thing as the oracle teacher of the teacher ablation below: the imitation term is a loss component whose weight is recorded in the config (hence imit edits appear in the loss slot); the oracle teacher (control/oracle/*) is a training-time curriculum invisible to TSConfig, which is why teacher vs no-teacher runs carry identical configs and differ only in their run-id tails.

Meta — everything else, possibly empty

Three kinds of items, in order: horizon when not the default normalized-time (full horizon, recursive window); config deviations from today's dataclass defaults (seed first, at most six spelled out, the rest folded into +N more) — fields frozen by a named recipe are excluded, which is why a simple-v1-lag arm shows a clean tail while a custom arm at the same capacity spells it out; and caller extras: campaign/arm for legacy runs, the run id for publisher-managed ones, pooled cohort for pooled trainings.

The +4 more on every legacy KSJC control arm is always the same four items — fleet=openap-direct, duration=uniform, duration-floor=0, grad-clip=20 — the campaign-wide dev settings, identical across arms, so they never distinguish two KSJC entries.

3 entries · Prediction

Imitation replication — campaigns imitation_replication, imitation_v5

Does KRDU's simple-v3 result replicate here? The loss slot answers directly: ksjc_baseline is exactly simple-v2 (640 m), ksjc_v3 exactly simple-v3 (664 m); v5_baseline re-ran the v2 baseline on a later manifest generation (656 m). The mechanism replicates and is stronger (bank skill 0.197 → 0.678, past the 0.543 same-runway twin ceiling) — but imitation weight 64 overshoots on KSJC (straight-in bank 0.18° vs flown 0.53°; FDE degrades on 68 % of flights), because bank carries only 18 % of the imitation term here vs 41 % at KRDU. Standing rule: recalibrate the weight per airport.

The bank-wiggle diagnosis — campaigns wiggle_*

Under simple-v1(-lag), position-only supervision let the model share one bank profile across flights. Four candidate causes were tested on identical data; the velocity dose was the one that mattered. Full write-up: docs/2026-08-19_control_bank_wiggle_diagnosis.zh.md.

The mechanical naming exposed something the old labels hid: the "velocity 2×" arm is exactly simple-v2 — 0.003 was frozen into the recipe because this ladder showed the 2× dose is the sweet spot (past 8× the bank drops below the flown tracks' own level while FDE climbs).

The other axes, all ruled out: conditioning — deep (layers=6, 725 m) and wide (d-model=1024, 686 m): width moved the shared share but per-flight skill stayed 0.000; segment count — n16 (710 m) and n32 (673 m): 12 pp shift, not even monotone (n16 shows no N= item — 16 is today's iTransformer default); training budget — batch128 (695 m) and lr3x (lr=0.0001, 670 m): the two ways of adding optimizer steps disagree; and the combination arm velocity2x_wide (689 m): with the velocity term present, width adds nothing.
