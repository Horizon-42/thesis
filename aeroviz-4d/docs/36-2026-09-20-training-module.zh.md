# Training 模块设计（2026-09-20）

前端加一个新任务页，叫 **Training**，放在 Observe 右边。它不训练模型、不算评估，只做一件事：
**把两层模型中间那些看不见的东西画出来** —— 一次进近被读成了哪几句话，这几句话本身意味着什么样的
航迹，以及（等模型训出来以后）模型自己说出来的那句话又意味着什么样的航迹。

这篇是设计文档，写在动手之前。实现按 §7 的步骤走，一步一评审。

## §2 放在哪，为什么

### 2.1 位置

`WorkbenchTopBar` 的任务条从

```
Observe │ Fly │ Optimize │ Compare ‖ Procedures
```

变成

```
Observe │ Training │ Fly │ Optimize │ Compare ‖ Procedures
```

代码上：`AppContext` 的 `WorkbenchMode` 联合类型加一个 `"training"`，`TASK_TABS` 加一项，
`WorkbenchLeftDock` 多一个分支。**不新增第二套模式系统** —— 仓库里已经因为"两套互相打架的 mode"
做过一次合并，不能倒回去。

### 2.2 为什么挨着 Observe 成立

- **看的是同一批飞机。** Observe 回答"真飞机是怎么飞的"，Training 回答"这条真航迹被读成了哪几句话"。
  两页共用顶栏的机场和跑道，也共用同一个航班身份（`flight_key` = `id_跑道_icao24_落地时刻`，
  不是呼号）。从 Observe 选中一架切到 Training，选中状态应该跟着走。
- **Fly / Optimize / Compare 是"造一条航迹出来"，Training 是"这条航迹被说成了什么"。** 它属于
  观测这一侧，不属于求解那一侧。放在 Observe 右边，读起来就是"同一批数据，下一个问题"。
- **它不抢 Observe 的资源。** `src/data/observedTracks.ts` 写明观测航迹的大文件只在 Observe 里加载
  （它会驱动共享的 Cesium 时钟，在别的任务里加载会把那边的播放顶掉）。Training 读自己的抽样文件，
  文件里自带需要的那几十条航迹，所以**不加载 Observe 的那份 CZML，也就不会抢时钟**。

### 2.3 它不是什么

不是"训练控制台"。不启动训练、不调后端、不写任何磁盘文件。它只读已经写好的 JSON。
真要跑训练，是命令行的事。

## §3 屏幕长什么样

三样东西，优先级就是用户给的顺序：

1. **一句话** —— 抽几架飞机，把从它航迹里读出来的指令词显示出来；
2. **这几个词允许的那片区域** —— 2026-09-21 傍晚起，词表是包围盒版：一个词是一个区间，
   一句话是一串盒子，所以"词说了什么"画出来是**一片区域**，不是一条线。三维里画的是
   高度楔形的那面墙，加上一串盒子；时间图上画的是每一刻生效的那个区间；
3. **模型说的句子** —— 同样画成**它自己的那串盒子**（紫色虚线），句子条在它说错的地方画紫条。
   注意它是**逐事件问出来的**，不是自由生成（V45）。这份词表上还没有训练好的先验。

**为什么没有"按规则飞出来的那条橙线"了**：飞一句包围盒需要一个**跟高度**的执行器 —— 词说的是
"待在这个高度区间里"，不是"用这个角度下降" —— 那就是回放门，还没做。硬画一条线出来，画的恰好
是这份词表唯一没说的东西（V53）。

句子条是这个模块的主角：一行一类词，横轴是**真实时间**，每个事件画一条竖线，
一类词在相邻几个事件上相同就并成一条带。

**盒子在时间上是铺满的**（这是包围盒版和旧读法最实在的一个差别）：每个盒子**自带**它保持多久
（时长词写在它描述的那一行），下一个盒子在它结束的地方开始。所以
`事件时刻 + 保持时长 = 下一个事件时刻`，最后一个盒子结束在航迹的最后一行 ——
**每一行都恰好有一个盒子生效，没有"最后一个事件之后那段没词的尾巴"**。
旧读法里那条尾巴中位 145 s，占一次进近的 44 %。读取器会检查这条铺满，缺一段就当场拒掉。

**时长行不并带**：它的词说的是"这个盒子保持 T 秒"，连着两个 4 s 的盒子是**两个盒子**，
并成一个 8 s 的带就是画了一句话里没有的话。

**横轴为什么必须是真实时间**：句子是事件序列，间隔本来就不均匀（保持时长中位 4 s、p95 20 s，
最长几十秒）。等宽排开会把 4 s 和 24 s 画成一样宽，而"几点几分说的这句话"正是要给人看的东西。

**句子条要按多大来画**（数来自产物自己的 `summary.json`，五机场 train 21 847 架）：

| 量 | 值 | 对排版的意思 |
|---|---|---|
| 每架的事件数 | 中位 **45**，均值 52.2，p95 **89** | 比旧读法（中位 4）多一个数量级。**带子很窄**：在 1 000 px 宽、260 s 的条上，一个 4 s 的盒子只有 15 px，写不下词 —— 所以窄带把标签丢掉、只留悬停，宽带才写（`LABEL_MIN_W` / `BAND_LABEL_MIN_W`） |
| 每架各类的词数 | 航向 19、**高度 26**、速度 8 | 高度最碎：楔形按剩余航迹收紧，一段只能延到楔形还装得下为止 |
| 保持时长 | 中位 **4 s**，p95 **20 s**，**35.8 % 不到 4 s** | 事件号和坐标轴刻度会挤成一团，所以两者都走"贪心留标签"（`spacedLabels`）：标签可以丢，事件本身和它的点击区不丢 |
| 各类用到的词数 | 航向 65/65、高度 48/61、速度 20/22 | 航向**每一档都用到了**；高度和速度没用满是梯子两端够不着，不是读法漏了 |
| 终止词 | 继续 + 落地；**复飞 0 次** | 落地数 = 航班数，"最后一个事件就是落地"是结构性的 |

**条上写的是区间，不是格心**（用户 2026-09-21：词表变了，呈现方式也要变）：

- **航向和速度直接写区间**（`−1…+1°`、`110–122 m/s`）：词本身就是区间，写一个中点等于自己
  编一个格心出来 —— 这份词表里没有格心这个东西；
- **高度写目标 + 它自己的那个盒子**（`1309 m±68.0`）：高度词说的是一个**目标高度**，
  ±68 是楔形在**段末**收到的那个盒子（目标的 ±5 %）。楔形在段的**开头**要宽得多，
  那是随剩余航迹变的，画在读数窗口的图上，不写在条上；
- **句子条的表头读出包含率**（`inside: heading 131/131 · altitude 131/131 · speed 131/131`）：
  这是这份词表**自己的判据**，所以放在表头而不是折叠起来。它是**前端自己按列重新算的**，
  不是从文件里读出来的数 —— 文件里那份已经在解析时和它对过了（V56）。

**它答的是什么**：

1. **三张图共一个时间游标**，和主屏、句子条、三维是同一个时刻；
2. **每张图的标题给包含率** —— `131 行全在盒子里`，或者 `128 / 131 行在盒子里 —— 3 行在外面`。
   这是这份词表的判据本身；
3. **出盒子的那几行画成红**，而且红线和标题那个数是**同一次判定**（一行一个判决，写进一个
   按行的数组再数出来，不是走一遍区间累加 —— 累加会把相邻两段共用的那一行数两遍，V33）；
4. **两条线，淡的那条是飞机**：盒子是从**平滑过**的信号上读出来的（航道 6 s、速度和高度 10 s），
   所以判决算在平滑线上，而原始行画在它后面。只画平滑线等于画了一条没人飞过的信号（V55）；
5. **高度那张图画的是楔形，不是带子**：词是一个目标高度，盒子是"这个目标倒着飞能到的那片区域"，
   段的开头宽、段末收到目标的 ±5 %。段末那根黄色短横就是目标本身；
6. **平面图上一个词一个地面脚印，是扇形不是长方体**：这一个词生效期间，航向词管住方向、
   速度词管住快慢，于是它能待的那块地是一个**从飞机那一点张开的扇形**（进深 = 保持时长 × 速度盒的
   **上界**，张角 = 航向盒）。它们**很窄**（中位 441 m 深、远端 23 m 宽），这个"窄"本身就是结论：
   横向上一个词几乎什么都没说，是整句话累起来才张开那个漏斗（设计 §5.1，未定）。
   **它是推出来的可达集，不是词本身** —— 词约束的是状态，不是路径，界面要说清是哪一个（V54）；
7. **模型说的那串盒子画成紫色虚线的框**，不填色，这样真值的盒子在底下还看得见；标题给出
   "它的盒子装得下多少行" —— 这才是模型真正被问的那个问题，比"对了几个词"更接近判据；
8. **航向是 wrapped 的**：盒子是**wrapped 相对航道角**上的区间，所以图必须和盒子在同一个坐标里。
   一架从 ±180 穿过去的飞机在这张图上会跳；而且平滑是在 wrapped 信号上做的，跨过那个断口时
   +179° 和 −179° 会被平均成 0° —— **这是标注器自己的算术，照抄不改**（V57）。

## §4 数据从哪来

### 4.1 谁写、写到哪

`aeroviz-4d/public/data` 不进 git（本地产物，由预处理脚本重新生成）。Training 的输入按同样的方式办：
**由一个新的 ts runner 写进去**，路径

```
aeroviz-4d/public/data/airports/<ICAO>/training/
    index.json                       有哪几个抽样集
    <集合 id>/sample.json            这一集的全部内容（航迹 + 句子 + 指令 + 几何航迹）
```

**为什么是 ts runner，不是 `aeroviz-4d/python/` 里的脚本**：那个目录下的 Python **不准 import 建模树**
（`aeroviz-4d/CLAUDE.md` 第一段），而导出必须调标注器（`manoeuvre/instructions.read_instructions`）、
必须通过 checkpoint 重建 cohort 的数据（`experiments/support.rebuild_cohort`）、还要用
`outputs/guidance/` 的常数飞几何航迹 —— 全是建模树。所以放

```
4dTrajectory/ts_transformer/experiments/instruction_sample_export.py
→ conda run -n aeroviz --no-capture-output python run_ts.py instruction_sample_export \
      --vocabulary 4dTrajectory/outputs/KRDU/experiments/two_tier_v3_bprime_20260920/vocabulary_tau10/instruction_vocabulary.json \
      --executor   4dTrajectory/outputs/KRDU/experiments/two_tier_v3_grid_20260918/L60_D60_s1337/checkpoint.pt \
      --out        aeroviz-4d/public/data/airports/KRDU/training/vocabulary_tau10 \
      --flights 40 [--split train]
```

**这就是 2026-09-20 22:44 实际跑的那条命令**（1.5 s，40/40 架重建）。跟原设计差两个参数，
都是 T3 落地时去掉的：**没有 `--cohort`**（checkpoint 自己带 data provenance，再给一个
cohort 文件就是第二处真相），**也没有 `--seed`**（抽样直接取 `hand_check/index.csv` 的前缀，
不复刻随机数，见 V20）。**`--executor` 填哪一个不要猜**：词表产物的
`instruction_vocabulary.json` 里 `source.executor` 写着它自己用的那一个，照抄。

**跑完必须重启前端**（`AV5`）。开着的 vite 看不到新建的目录，`index.json` 会按 SPA 兜底
返回 HTML，前端报的是"收到 HTML 不是 JSON"。这台机器上前端挂在
`start_aeroviz_fullstack.sh` 下面，杀掉 vite 那个进程组、让 supervisor 重起一个即可。

checkpoint 在这里只是"进数据的门"（C25：通过它的 data provenance 重建同一批飞机），不读它的权重。
抽样分层与 B0′ 的人工核同一套：一半直线进近、一半雷达引导，种子给定，短了就报错不偷偷补。

### 4.3 `sample.json`

**包围盒版的契约（`aeroviz-training-sample-v2`，2026-09-21 傍晚）。** 这份文件和上一版是**两个东西**，

**两个表的长度不一样，这是最容易读错的一处**：航向和速度是**边界表**，铺满它们的词，所以比词数
多一个；高度是**目标梯子**，一个词一个目标。读反了会把每个高度词平移半个盒子，而且照样画得出来 ——
所以读取器从表里**自己推一遍类别数**，和文件自己写的 `words` 对，对不上就拒（V50 的延续）。

一架飞机：

```json
{
  "flightKey": "DAL1337_05R_ab1234_…", "callsign": "DAL1337",
  "runway": "KRDU:05R", "stratum": "straight-in",
  "durationS": 260.0,
  "dtS": 2.0, "courseWindowRows": 4, "signalWindowRows": 6,
  "sentence": {
    "eventTimesS": [0, 18, 34, …],       // 严格递增，第一个是 0
    "holdS":       [18, 16, 28, …],      // = 时长词 × 2 s，读取器对过
    "words":       [[…6 列…], …]         // kinds 的顺序，位置定含义
  },
  "observed": {                          // 跑道坐标系下的观测航迹，一行一个时刻
    "tS", "toGoM", "crossM", "heightM", "pathM",
    "relCourseDeg", "groundSpeedMps", "established",
    "readCourseDeg", "readSpeedMps", "readHeightM",   // 盒子判的那三路（平滑过）
    "lon", "lat", "altHaeM", "haeOffsetM"             // 三维用；haeOffsetM 见下
  },
  "envelope": {                          // 这句话在这条航迹上做出来的那串盒子
    "altLoM", "altHiM", "altHaeLoM", "altHaeHiM",     // 楔形，**按行**（它沿段收紧）
    "events": [ {                        // 一个词一个盒子(脚印是扇形的外轮廓)
      "eventS", "holdS",
      "headingLoDeg", "headingHiDeg", "speedLoMps", "speedHiMps",
      "altitudeTargetM", "altLoM", "altHiM", "altHaeLoM", "altHaeHiM",
      "lon": [N], "lat": [N], "toGoM": [N], "crossM": [N]   // 地面脚印：扇形的外轮廓，
                                                            // 第一个点是顶点（飞机自己）
    } ],
    "inside": { "heading": {"rows": 131, "outside": 0}, "altitude": {…}, "speed": {…} }
  },
  "prior": { … 只有 `prior-generated` 那一类的集合才有；见下 … }
}
```

**为什么楔形按行、航向速度按事件**：航向词和速度词在生效期间是同一个区间，写一次就够；
高度的盒子**沿着段收紧**（剩的航迹越少、楔形越窄），所以只能一行一个数。

**`haeOffsetM` 是那次垂直基准换算做成的一个偏移量**：把"入口以上的高度"加上它就是椭球高（HAE）。
记录是 MSL，Cesium 的 `cartographicDegrees` 读的是椭球高，KRDU 的 N ≈ −33.5 m，**N 是负的，
所以拿 MSL 当 HAE 喂进去线会偏高 33.5 m**。楔形另外有四列高度要换算，把换算写成一个偏移量
就只做一次大地测量反算，五列不会各自漂（V58）。

**`inside` 要算两遍，这是这份产物没有源码的代价**（§1）。导出器按产物自己的 spec 重建盒子并算一遍，
前端拿着它送来的那些列**再算一遍**，两个数对不上就拒掉整份文件。一份通过的文件是被判过两次的。
同一个 `insideEpsilon`（0.001）两边都用：文件里的列是按显示精度写的、边界表是全精度的，而标注器的
贪心读法**按构造**会把一些行留在盒子的边上（实测 13 922 行里有一行），没有这个数它们会读成
一万亿分之一米的越界。

**文件会多大**：KRDU 40 架 **5.9 MB**。楔形四列 + 一个词一个扇形加起来大约每架多 2 000 个数
（扇形按张角取 3–16 个点，中位 4 个），比上一版的走廊（每架 5 300 个数）还省 ——
上一版要带两条完整的速度边界航迹。

### 4.4 词表的四条性质，界面必须体现

这四条是 2026-09-20 当天定下来的，写在这里是因为它们直接决定界面画什么、不画什么。
第四条是**最容易画错的一条**。

**一、句子是一串包围盒，在时间上铺满；词是六类。**（当前读法 **`box-v3`**。
2026-09-20 第一次改：从等间隔网格改成事件序列；2026-09-21 傍晚第二次改：一个词从一个**格心**
变成一个**区间**。）

一句话是一串**事件**。每个事件说"从此刻起、持续 T 秒，这架飞机待在这几个区间里"。
判据是**包含**：航迹的每一行都必须落在当时生效的那几个区间内。三个后果，界面必须体现：

- **没有格心，也没有量化误差这个量** —— 旧界面上"离格子中心多远"那类读数全部取消；
- **容差就是词本身**，因此**进 sha**：冗余 0.05、航向地板 1°、高度楔形的两个角和那把梯子，
  全在 `vocabulary.sha256` 里。界面列词表的时候要把这些数列出来，只列类别数等于
  说了这份词表的形状、一个字没说它的含义；
- **盒子铺满、不留空洞、两端有界**。时间上铺满（每个盒子自带它保持多久，下一个接着开），
  取值上也铺满（航向铺满 −180…180，速度铺满 30…271 m/s）。**没有射线**：射线装得下任何值，
  一行坏数据会变成一个合法的词。

六类词，**顺序写死，列是按位置认的**：

| 列 | 类 | 说的是什么 | 几类 |
|---|---|---|---|
| 0 | 航向 | 相对最后进近航道的地面航迹角，一个**区间**；半宽 `max(1°, 5 % × 值)`，所以航道处 2° 宽、反航向 18° 宽 | 65 |
| 1 | **高度** | 一个**目标高度**（入口以上，有符号梯子 −133…5469 m），它的盒子是这个目标的**后向可达楔形**：往上张 1.5°、往下张 1.0°，段末收到目标的 ±5 % | 61 |
| 2 | 速度 | **地速**，一个区间，半宽 5 %；铺满 30…271 m/s | 22 |
| 3 | 跑道 | **不是包围盒的一维，是包围盒的坐标系** —— 决定其余三个量相对谁量。带机场前缀（`KRDU:05R`） | 22（五机场） |
| 4 | 时长 | 这个盒子保持多久，2 s 一格到 600 s。**写在它描述的那一行**，不是"距上一个事件多久" | 301 |
| 5 | 终止 | 0 继续 / 1 落地 / 2 复飞 | 3 |

**时长词换了位置，这一条会画错**：旧读法里它量的是**前面**那一段，所以句子条上它要画在事件
**左边**；现在它量的是**自己这一个盒子**，画在事件右边，而且**不能并带** —— 连着两个 4 s 的
盒子是两个盒子。换过来画会把整行往前错一格。

**高度词不是航迹倾角**（那是 2026-09-21 白天那一版，已作废）：角度盒约束的是高度**变化率**，
界定不了"降到哪"；楔形约束的是高度本身，所以它是这份词表里**唯一一个绝对的位置界**。
界面上凡是原来画"下降为正的角度、带箭头"的地方，现在画的是"目标高度 + 它周围那片楔形"。

**终止词的"复飞"这一类在这份数据里从不出现** —— 25 km 到达切片只留最后那次成功的进近
（第三条）。图例里**可以**把三类都列出来，但要写明"复飞：本数据中从未观测到"，
**不能写成"模型不肯用它"** —— 一个从没见过的类别和一个模型拒绝使用的类别，是两回事。

**跑道那一列为什么非有不可**（计划的决定 D62）：航向和高度全是**相对某一条跑道**量出来的
（航向相对最后进近航道、高度相对跑道入口），所以一句没有跑道词的话**说不出"去哪条跑道"**；
而且真实管制里跑道本来就是管制员要说出口的一句话。
→ **界面只要显示一句话，就必须同时显示这句话是对哪条跑道说的**，并写明别的类是相对它量的。
这不是装饰：同一串航向词配不同的跑道词，指的是完全不同的两条航迹。

**二、跑道词不在词表的 sha 里。** 跑道词的类别集合是**每个机场各一套**，它挂在词表产物的 spec
**旁边**（`runway_idents`），不进 `sha256`；做法和机型词表（`manoeuvre.context.TypeVocabulary`）
一样。为什么这么设计：进了 sha，一份词表就不能通用于五个机场了。
**后果，界面上要认这个后果**：两份 sha 相同的产物，跑道类别集合可以不一样。所以
`instructions.py` 另有一个 `runway_sha256(runway_vocabulary)`（第 350 行），先验的产物里
这两个 sha 是**分开两个字段**存的（`experiments/instruction_prior.py` 第 156–157、166–167 行）。
Training 的 `index.json` / `sample.json` 照抄这个做法：`vocabularySha256` 和 `runwaySha256`
各是一个字段。**只比对其中一个就当成"同一份词表"是错的。**

**注意一个坑**：`runway_sha256` **不是词表产物文件里的一个字段**（`instruction_vocabulary.json`
的顶层只有 `schema / written_utc / spec / sha256 / runway_idents / words / cohort_identity /
counts / source` —— 我开文件核过）。它是一个**函数**，导出器要拿 `runway_idents` 建出
`RunwayVocabulary` 再调它算出来。T3 不要去文件里找这个字段，找不到。

**三、"复飞"这个类别存在，但在这份数据里从不触发。** 这一条量过才定的（结果文档 §13.5）：
复飞在机队里是真的 —— 五个机场 44 622 条航迹里有 42 条（0.094 %，和公开的复飞率同量级，
逐架核过剖面）—— 但**词表是在 25 km 到达切片上读的，切片只留最后那一次成功的进近**，
所以复飞在这个 cohort 里一次也不会触发。它现在是终止词的第 2 类（不是一个单独的词类），
**界面按"有这个类别、但本数据从未观测到"来画**：图例里可以列出，旁边必须写明从未观测到。
不要画成一个永远空着的计数槽，也不要让人读成"模型不肯说复飞"。这是这份数据的一条限制：
**本阶段的句子表达不了"这次不落地"**；要改得动上游的到达窗口，那会改掉每一个 ts 数据集划分，
不在这个模块的范围内。这句限制要写在读数核对窗口的说明里，不然看的人会以为是读漏了。

**同一条规矩也适用于这个模块自己**：一个永远不会被设置的字段、一个永远不会亮的提示条，
就不要建。（用户 2026-09-20 否掉"从 `_superseded/` 导一份临时数据"时，`supersededSource`
标志和它配的红条就一起删掉了，不留在设计里。）

**四、跑道词的类别要从产物里读，绝不能从 `runway.geojson` 读。** 这是最容易画错的一条，
因为两边在 KRDU 就对不上：

| | 有哪几条 | 几条 |
|---|---|---|
| 机场的跑道表（`public/data/airports/KRDU/runway.geojson`、`landings/index.json`） | 05L 05R **14** 23L 23R **32** | 6 |

## §5 包围盒怎么画出来（2026-09-21 傍晚，取代"词怎么画成航迹"）

### 5.1 换掉了什么，为什么

旧的 §5 是一套运动学：一句话给三个目标（转到某个角度、按某个倾角飞、减到某个地速），
补一套最简单的执行器把它飞出来，画成一条橙线。**包围盒版之后这条线没有了**，原因不是它不好用，
而是它画的东西这份词表不说：

- 高度词现在说的是"待在这个高度区间里"，不是"用这个角度下降"。要把它飞出来，需要一个**跟高度**
  的执行器 —— 那是设计文档里的**回放门**，还没做；
- 硬拿一个角度去飞（比如取楔形的中线），画出来的那条线是**我们自己编的**，它的形状取决于那个
  选择而不是取决于词。一条看起来很合理、但唯一来源是画图代码的线，比不画更糟（V53）。

所以现在画的是**词允许的那片区域**，判据也跟着换了：不再问"两条线差多远"，而问
**"这片区域装不装得下这架飞机"**。

### 5.2 三样东西：楔形的墙、一串盒子、包含判决

| 画什么 | 是什么 | 在哪画 |
|---|---|---|
| **楔形的墙** | 高度词的盒子，沿飞机自己的地面航迹立起来的墙。段的开头宽、段末收到目标的 ±5 %。**一段一面墙，不是一架一面**：高度界在每一个高度词处**跳一下**（这一段收到目标，下一段重新张开；一架引导进近上实测 9 次跳、最大 59 m），一面墙硬穿过这些跳，在转弯的地面航迹上会渲染成**扭曲的面** —— 那就是"扭曲弧线"的来源。拆开之后每一面都干净地收窄，两面之间的那一跳看上去就是一跳 | 三维（一段一个 Cesium `wall`）、读数窗口的高度图 |
| **一串锥台** | 一个词一块空间：平面上是**从飞机那一点张开的扇形**，竖直方向**跟着收** —— 越往外，离这一段高度的段末越近，楔形越窄。所以它是一个**锥台**：平面是扇形，任何一条径向剖面是**梯形** | 三维（一个词一个 `wall` + 一张斜的顶盖）、读数窗口的平面图（地面脚印） |
| **包含判决** | 每一行在不在当刻生效的盒子里 | 句子条表头、读数窗口每张图的标题、图上的红色段 |

**楔形是这份词表里唯一一个绝对的位置界。** 航向盒和速度盒只给**位移**界，随时间张开；
水平方向没有绝对界，这是设计文档 §5.1 的已知洞。所以三维里那面墙是"这架飞机的高度必须在这里"，
而那串盒子是"这一个词允许它走到哪"——**两句话不一样，界面要分开说**。

### 5.3 一个词的地面脚印是**扇形**，不是长方体（2026-09-21，用户指出）

**先分清两个空间。** 词表说的"包围盒"是**状态空间**里的盒子：航向区间 × 速度区间 × 高度区间。
它在**位置空间**里推出来的那块地**不是盒子** —— 是一个从飞机自己那一点张开的**扇形**。

一个词生效 T 秒，期间地面航迹角在 `[ψ_lo, ψ_hi]`、地速在 `[v_lo, v_hi]`。那么这段时间里它能在的位置是

```
{ ∫₀^τ v(s)·(cos ψ(s), sin ψ(s)) ds : τ ∈ [0,T], v(s) ∈ [v_lo,v_hi], ψ(s) ∈ [ψ_lo,ψ_hi] }
```

集值映射在 [0, τ] 上的积分是 `τ · conv(V)`，τ 从 0 扫到 T 又把这个凸包一路缩回原点，
所以这个集合正好是：**顶点在飞机、半径 `T · v_hi`、张角等于航向盒**的那块扇形。

两条要写明的：

- **速度盒的下界根本不约束它。** 下界说的是"保持结束那一刻它至少飞了 `T·v_lo`"；
  但在结束之前的任何一刻它都还更近，所以扫过的区域一直连回顶点。**只有上界决定半径。**
- **它的外接长方体不是它。** 第一版画的就是外接长方体，那是错的，而且错在要紧的地方：
  长方体在**顶点旁边**多出一块地，那块地**航向盒里的任何一个方向都到不了** ——
  看上去像可飞空间，其实不是。2° 的盒子长方体面积约是扇形的两倍，9° 的更糟；
  更重要的是它把这个形状唯一要表达的事情盖掉了：**这块区域是从飞机那一点张开的**。

实测（KRDU 40 架、2 252 个词）：**进深中位 441 m，远端宽度中位 23 m**；p95 是 2 923 m 深、
418 m 宽；最大的一个 21.5 km 深（一段很长的直线保持）。这个"窄"本身就是读数：
**横向上一个词几乎什么都没说**，是整句话累起来才张开那个漏斗（25 km 外半宽约 14 km）。

弧上取几个点：**按张角每度一个**，下限 3、上限 16。取常数要么把宽的画成折线，
要么在一条细缝上花十六个点。

两件必须说清的事：

1. **它是推出来的可达集，不是词本身。** 词约束的是**每一时刻的状态**，不是路径；
   "这让飞机能走到哪"是从词推出来的第二件事。界面上这两者要分开说（V54）。
2. **它里面没有飞机。** 没有任何东西限制航向在盒子里**转多快** —— 因为词不限制。
   转弯速率是执行器的规矩，这份文件里没有执行器。所以扇形是"词允许的位置"，
   **比真正飞得到的那块地大**；把转弯速率加回去就等于把执行器的假设偷偷加回来。

**竖直方向也要跟着收（2026-09-21 晚，用户再次指出）。** 第一版给整个立体一个高度区间、平平地拉起来，
那是错的：外轮廓上离顶点 `d` 米的那个点，**到这一段高度的段末就少了 `d` 米航迹**（直线是过去最短的
走法，绕的只会更少），所以那里的楔形是 `wedge(r₀ − d)`，比顶点窄。**一个平的盖子，是这份词表唯一
没说过的东西**；按一个高度拉平，在长保持上会把远端的天花板抬高到**盒子自身高度的 26 %**。

所以每个词的立体是一个**锥台**：平面上是扇形，任何一条径向剖面是**梯形**。文件里的做法是
**外轮廓上每一个点带一对高度**（顶点那一对最高，弧上那一对最低）。三维里画成一圈
`wall`（首尾闭回顶点，所以两个径向面 —— 也就是那两个梯形 —— 都画得出来）加一张
`perPositionHeight` 的斜顶盖；`polygon` 的 `extrudedHeight` 只能给一个数，表达不了斜的盖子。

扇形在**导出器**那一侧算，算完给出经纬度和跑道坐标系两套坐标，**第一个点是顶点**。
理由是坐标系的变换在那一侧：前端只有一条航迹的经纬度列，没有办法把一个任意的
（沿航道距离、横向距离）放到地图上。

### 5.4 盒子判的是哪条信号 —— 这一条决定判决本身

**盒子是从平滑过的信号上读出来的**，所以判决必须算在同一条信号上。这不是细节，是那个数本身：
同一条航迹、同一批盒子，算在平滑信号上是 **100 % 在盒子里**，算在原始行上是 **93 %**。

| 量 | 盒子判的那条 | 窗口 |
|---|---|---|
| 航向 | `wrap(**unwrapped** 相对航道角的滑动平均)` —— **box-v3 改的就是这一条** | `course_smoothing_s` = 6 s |
| 速度 | 地速的滑动平均 | `smoothing_s` = 10 s |
| 高度 | 入口以上高度的滑动平均 | `smoothing_s` = 10 s |
| 楔形的剩余航迹 | **平滑后**的地速积分 | 同上 |

这四行**不是猜的，是量出来的**：每一行都试过两三种写法，取那个把产物自己接受的航迹 100 % 装进盒子
的那一种。剩余航迹若用原始地速积分，最大越界 0.3 mm，用平滑地速是 0.005 mm。

**航向这一条在 box-v3 翻了过来，这是两版之间唯一实质的读法差别。**

| 写法 | box-v2-wedge | **box-v3** |
|---|---|---|
| `wrap(smooth(wrapped))` | **100 %** | 98.6 % |
| `wrap(smooth(unwrapped))` | 97.5 % | **100 %** |
| 圆周平均（把单位向量平均再取角） | — | **100 %** |
| 原始 wrapped，不平滑 | 93.9 % | 93.9 % |

旧写法在 ±180 附近会把 +179° 和 −179° **平均成 0°**；按它重建，落在盒外的那 1.4 % 行**全部**在那个
断口附近（实测最远的一行：航向盒 `[-180, -171.79]`，重建出来的值是 `0.63°`）。新读法修的就是它。

**圆周平均和 unwrapped 在这批数据上分不开**（13 922 行全对）。两者只在"unwrap 累积了整整一圈"
的航迹上才会分家；这里取 unwrapped，因为 `course_frame` 本来就带着这一列。真要有一架把两者
分开的飞机，**包含率就是那个发现它的人**（V60）。

原始行照样导出、照样画（淡线在后面）。只画平滑线等于画了一条没人飞过的信号（V55）。

### 5.5 现在是 import，不是重建（2026-09-21 晚）

**标注器进仓库了**（`manoeuvre/box_vocabulary.py`，§1）。在那之前这一节写的是"照 spec 重建、拿包含率
顶替和原件对一遍"；现在原件在手，换成三层检查：

1. **spec 回算的 sha 必须等于产物写的那个。** sha 只盖 spec，所以这一条恰好在"产物和这边对 spec 的
   读法不一致"时失败 —— 那是比对一个读法名字的字符串看不见的失败。
2. **产物带的三张表必须等于 `BoxVocabulary` 推出来的。** 两种写法，一件事；它们一致，产物那一份才
   是检查而不是第二意见。文件里发出去的是**推出来的那一份**。
3. **每一架都用 `read_boxes` 重读一遍。** 句子是从产物抄的、航迹是这边重建的，除了这一条没有任何东西
   说它们是同一架飞机。重读出来的词和时刻必须逐个相同 —— 这比它取代的"时长对得上"强：一条长度
   对、但不是那一条的航迹会被它抓住。

**重建期间漏掉的三处，import 之后都露出来了**（每一处都不会让当时发的那批数据变红，这正是它们的可怕之处）：

| 漏掉的 | 后果 |
|---|---|
| `altitude_half_width` 取的是 **\|T\|**，我写成了 `T` | 梯子上 **61 个目标里有 13 个是负的**（它要跨过入口高程）。`0.05·(T+50)` 在 T = −50 处归零、再往下变负 —— 那是一个**上下界翻过来**的盒子，谁也待不进去 |
| 段末取的是**这一段自己的最后一行**，我取的是下一个高度事件的时刻 | 差一行的航迹长度，80 m/s 下是 4 m 的楔形 |
| 路径积分**不加地速下限**，我加了 | 这支机队上永远不 binding（所以当时重建出来差 5e-6 m），但那不是保留一处差别的理由 |

前端那一侧仍然**再算一遍**包含率（拿导出器送来的列），两个数对不上就**拒掉整份文件**。

**列序也得自己钉。** `box-v3` 把 `spec.kinds` 去掉了，于是"哪一列是哪一类"在文件里没有任何一处
写着。导出器改成拿**文件自己的数据**去对（`check_columns`），这比对一个字符串本来就更实在：

- **跑道列**必须每一个事件都等于这架飞机自己那条跑道在类别表里的下标；
- **时长列**乘上格宽必须等于旁边的 `hold_s`；
- **终止列**必须是一路"继续"到最后一个事件的"落地"。

这三条钉住三列。另外三列（航向、高度、速度）由**包含率本身**钉住 —— 两列对调的话，几乎每一行都会
掉到盒子外面。

这是两份独立实现的同一个比较，顶替"和原件对一遍"。一份通过的文件是被判过两次的。
两边用同一个 `insideEpsilon`（0.001）：标注器的贪心读法**按构造**会把一些行留在盒子的边上，
没有这个数它们会读成一万亿分之一米的越界（V56）。

**这条要在词表那边的代码进仓库之后换掉**，换成真正的单一来源（import 而不是重建）。
在那之前，五机场 200 架 **39 670 / 39 670 行全在盒子里**是这个重建唯一的凭据。

### 5.6 它是诊断，不是模型的答案

和旧的 §5.5 一样成立，换了对象：**这片区域是词表能说什么的诊断，不是任何模型的输出**。
"航迹在盒子里"只说明这句话装得下这架飞机；它**不**说明这句话能被飞出来、也不说明
它能落地 —— 那是链条条件和回放门的事，都还没算（词表设计 §3.4 / §5.3）。
界面上任何一处都不要把包含率说成一个模型指标。


## §6 v1 不做什么

写清楚，免得后面有人以为忘了：

1. **不能在界面上改一个词再重飞。** 那需要把 §5.3 的运动学搬进浏览器（等于制造第二份定义），
   或者给后端加一个端点。**第二条路是 v2 的方向**（`aeroviz_backend` 加
   `POST /training/fly-sentence`，收一串词返回一条航迹），v1 不做。
2. **不做人工核的判定录入**（一致 / 漏读 / 误读）。那是实验产物，要进带 sha 的 artefact，
   不能进浏览器的本地存储（本地存储只在这台浏览器里，Claude 和别人都读不到）。
3. **不浏览全体**。B cohort 是 train 6853 / val 1404 架；导出是**抽样**，份额和种子写在
   `index.json` 里，界面上明写"这是 40 架的抽样"。不做无声的截断。
4. **面板三（模型说的句子）v1 只有占位**，因为阶段 B3′ 还没跑，没有产物。占位要说清楚在等什么。
5. **不做 τ = 5 s 的对照**（计划的 B4′）。两个 τ 只是两个集合，等有了产物自然就能并排看。
6. **不改 Observe、不改比较视图**。Training 只新增文件，不动既有任务页的行为。
7. **不做多机**（阶段 C 之后的事）。
8. **不做演示模式的特别排版**（`presentationMode`），v1 沿用左坞 + 底栏。

## §7 步骤（按这个顺序做，一步一评审）

## §8 决定项（做了什么选择，为什么）

| # | 决定 | 理由 | 谁定的 |
|---|---|---|---|
| V1 | Training 是第五个任务页，放 Observe 右边，共用顶栏的机场/跑道和选中的航班 | 看的是同一批飞机的同一件事的下一个问题；不新建第二套模式系统 | 用户指定位置；其余我定 |
| V2 | Training **不加载** Observe 的观测 CZML，自带抽样文件 | 那份大文件会驱动共享时钟，在别的任务里加载会顶掉播放（`observedTracks.ts` 写明） | 我定 |
| V3 | 输入由**新的 ts runner** 写进 `public/data/airports/<ICAO>/training/` | `aeroviz-4d/python/` 不准 import 建模树，而导出必须调标注器和 cohort 重建 | 仓库规矩 |
| V4 | 抽样文件里**自带航迹**（跑道坐标系 + 经纬高），不复用 CZML | 三张时间图要的量 CZML 里没有；抽样集是绑 sha 的只读快照 | 我定 |
